# minime-code-simplifier


Simplify implementation code without changing documented behavior. Use for
targeted refactoring, de-duplication, dead-code removal, or complexity
reduction.

DRY and YAGNI are mandatory simplification lenses:
- **DRY:** remove duplicated logic, repeated tests, repeated docs generated by
  the code change, and parallel helper paths unless a standalone-consumption or
  authority boundary requires separate copies.
- **YAGNI:** remove or avoid code, flags, config, abstractions, and schema fields
  that have no current requirement, caller, test, or accepted decision.

## When to use

- Use as a post-implementation pass for every code change; may conclude
  already appropriately simple.
- Use for targeted refactoring, de-duplication, or complexity reduction.
- Do not change documented behavior; do not weaken validation, audit,
  idempotency, or authority rules.

## Non-negotiables

Reject any refactor that violates these:
- No behavior change beyond the stated task.
- Do not weaken validation, audit, idempotency, or authority rules.
- Do not cross architecture boundaries casually.
- Do not remove tests unless they are obsolete and replaced.
- Remove or avoid abstractions that do not serve at least two concrete uses
  or a documented invariant.
- Do not add generic frameworks, unused layers, flags, or config as part of
  simplification.
- Do not keep duplicated logic or process text without a load-bearing reason.
- Do not preserve unused extension points for possible future work.
- Preserve behavior-focused tests; do not replace them with structure-only
  tests.
- Follow with tests and review after any risky simplification.
- When a simplification would change observable behavior, stop and route to
  a human checkpoint.

## Procedure

1. Identify behavior governed by requirements, decisions, and architecture
   docs.
2. Characterize current complexity: duplicated logic or text, unnecessary
   abstractions, unclear names, one-off pipelines, unused extension points.
3. Propose the smallest safe refactor; if none is needed, state this
   explicitly and stop.
4. When required by the project guide, confirm with the user before
   starting.
5. Apply the project's quality guard if the refactor introduces or removes
   an abstraction, boundary, flag, or error-handling strategy.
6. Preserve or add tests before changing risky code.
7. Apply post-implementation completion gates as defined in the project
   guide.

## Skeptic pass

- Do not trust comments, docstrings, or commit messages about behavior;
  verify from tests and code.
- Assume any abstraction labelled for future use has no current caller until
  you find one.
- Stop if you cannot identify which requirement or decision governs a code
  block you intend to remove.
- Reject any simplification that removes behavior currently asserted by a
  test or stated by a documented invariant — even if the code path looks
  dead.
- A simpler diff that flattens an architectural role boundary is not
  simplification; it is regression.

## Output

- Target files
- Behavior preserved
- Change summary
- Risks
- Tests to run or add
- Docs impacted

## Interaction rules

- End with `Recommended next action: <one concrete step>`. If that step is a
  check or gate that needs no user input, run it now instead of stopping.
- Before a feature or behavior change, check it against accepted requirements
  and decisions, name its impact, and confirm its value; route non-trivial
  cases through `minime-course-correction-triage`.
- Ask any question whose answer changes an artifact through
  `minime-decision-prompt`: one question per turn, named options with pros,
  cons and impact, in the host's choice UI when available.
- Never skip a failing test, lint, type or doc check because it pre-existed;
  fix it or escalate before committing.
- When a step names another skill, read that skill's file and follow its full
  procedure.
